# Billing workflow, idempotency, transactions and recovery evidence

Reviewed source: `a1af92129f60728a0bbcf0dd27c42190644b1e3b`. Read-only investigation. No database, configuration, production code, credential or infrastructure access. This reviewer did not execute tests; the coordinating reviewer supplies current execution results. Existing test methods below were inspected, not assumed to pass.

## Part 3 — Progress notes and billing workflow

**Evidence classification: Partially implemented for the complete external billing lifecycle.** The internal and synthetic lifecycle has considerable implementation and test coverage; live payer certification and a production-capable transport are not established.

Clinical approval, financial eligibility, clearinghouse receipt, payer acceptance, adjudication and bank receipt are separate facts. Sati actually implements this separation. Normal approval changes the note to Approved, records approver/time, increments its revision and records a minimal approval audit in a transaction; it does not create a claim or claim that money was paid (`Sati.Api/Endpoints/ApiEndpoints.cs:1780-1835`). It checks the current scoped reviewer, expected revision and overlapping service time. The authoritative note transition table is `Sati.Contracts/V1/NoteWorkflow.cs`.

The billing queue is a query, not a second table filled by a fragile approval notification. `BillingCandidateBaseQuery` selects approved notes, excludes ordinary Unbilled notes, financial-amendment holds and notes already represented by a ClaimLine, and requires matching note/person/owner agency (`Sati.Api/Endpoints/ApiEndpoints.cs:10417-10461`). GET `/billing/candidates` projects approved financial amendments and returns computed validation problems, using current effective compliance policy, form attestations, releases, provider links, monthly contact and recovery decisions (`:6801-6851`). Consequently, a note can be approved yet held from financial promotion. Some candidate rows are shown with errors; reasons causing exclusion are not themselves saved as historical events.

Billing personnel promote an eligible note through POST `/billing/claim-lines`. The API requires Billing permission, checks source agency/status, acquires a serializable billing-period write scope, freshly checks the actor and source, refuses a second claim line for the note, validates documentation/identifiers/compliance/payer preparation and overlap, freezes the claim inputs, validates exact 837 readiness, and commits the claim plus audit together (`ApiEndpoints.cs:6854-7025`). `BillingPeriodWriteScope` adds SQL Server `sp_getapplock`, keyed by agency/owner/year/month, so multiple API processes coordinate their changes (`Sati.Persistence/Data/BillingPeriodWriteScope.cs:15-66`).

The claim freezes service date, procedure/modifier, units, charge, member/provider/diagnosis/POS and a versioned subscriber/provider/submitter/payer snapshot (`ApiEndpoints.cs:6969-7004`). Current configured payer claims add a versioned effective payer configuration and reviewed manual authorization evidence. `PayerBillingRules.ValidatePreparation` checks person/profile/procedure/rendering scope, decision date, coverage dates, reviewed evidence and modifiers (`Sati.Contracts/V1/PayerBilling.cs:155-184`). **This is validation of an operator's evidence reference, not an authoritative payer authorization or utilization balance.** A server-owned authorization aggregate and utilization ledger remain deferred (`AGENDA.md:9153-9163`).

Period submission is a local financial locking step: draft→submitted, fresh readiness and compliance checks, submitted time and audit in a transaction; replay of an already submitted period returns its existing state (`ApiEndpoints.cs:7046-7118`). It is not external transmission. Return-to-draft refuses EDI/exchange history (`:7121-7182`). Generation requires a submitted nonempty period and a GUID idempotency key, rechecks current permission, source, service time and effective historical compliance including form work, then retains exact 837P bytes, the generation identity, Generated event and audit before returning the file (`:7185-7298`; `Sati.Api/Endpoints/ApiEndpoints.BillingExport.cs:14-114`).

`ServerEdiGenerator` maps persistence into the shared `Professional837Formatter`; originals contain every line at frequency 1 (`Sati.Api/Infrastructure/ServerEdiGenerator.cs:9-44`). The formatter implements the 5010 837P envelope, subscriber/provider/payer loops, claim/line identities, charges and service dates. Configured v2 claims include rendering and service-facility loops and facility REF, prior authorization REF G1, Claim.MD stable REF D9, and corrected/void payer REF F8 (`Sati.Contracts/V1/Professional837Formatter.cs:25-121`). Older runbook text saying service-facility output is absent is superseded by this implementation. Output correctness for supported synthetic fixtures does not establish payer enrollment, companion-guide applicability or vendor certification. The current v2 scope remains a single-line Section 13 unit basis; no general multi-line utilization ledger.

There are two materially different operating paths. Cloud Demo implements HTTP billing/export/response/correction/dispatch services (`Data/Cloud/CloudUnavailableServices.cs:605-825`; the filename is historical and does not mean these classes are stubs). The workstation's local working environment retains `BillingService` and `EdiService` with EF and generates Office Ally files to `%LOCALAPPDATA%/Sati/EDI`, committing generation/audit before disk output (`Data/Billing/IdeService.cs:29-118,198-203`). Response import, server dispatch and claimed-note correction adapters are unavailable through the default local service contract (`Data/Billing/IBillingService.cs:19-36,105-125`; `AGENDA.md:9160-9163`).

Server dispatch is a durable database outbox. Billing staff queue an exact retained test generation/account after tenant/account/profile and prior-transmission checks; the command writes dispatch and queue audit atomically (`Sati.Api/Endpoints/ClearinghouseDispatchEndpoints.cs:67-157`). A background worker sends it later. **The actual gate only allows exact Demo/Testing environments and test-mode accounts/files, with explicit server opt-in.** It cannot send Production claims (`Sati.Api/Infrastructure/ClearinghouseDispatchGate.cs:12-26`). The real Claim.MD sandbox connector targets a fixed HTTPS host, sends server-resolved AccountKey and immutable 837P bytes, verifies returned file/PCN/D9/count/status identity, and treats malformed or ambiguous output as unknown (`Sati.Api/Infrastructure/ClaimMdSandboxConnector.cs:44-102`). No real vendor call or account was used by this assessment.

999 and 277CA are implemented as bounded manual/mock X12 intake; Claim.MD API status XML is explicitly a different source. `ClaimResponseIngestion` matches a 999 to the original group/transaction and 277CA/835 to retained claim/line identities, amounts, direction/environment and payee; it refuses ambiguous/unmatched documents (`Sati.Api/Infrastructure/ClaimResponseIngestion.cs:232-297`). `ClaimResponseReader` rejects unsupported/malformed structures instead of silently posting financial effects. Receipt originals are encrypted and retained with provenance, hash and immutable matches. 835 processing writes claim outcomes, payer claim number, monetary adjustments, deposit information and appropriate paid/partial/review stages atomically (`ClaimResponseIngestion.cs:300-371`). A second payment/reversal for a claim needs review; paid 835 does not automatically establish actual bank receipt. Bank deposit records and corrections are append-only (`Sati.Api/Endpoints/BillingCorrectionEndpoints.cs:22-108`; `Sati.Contracts/V1/ClaimCorrectionRules.cs:220-286`).

Claim.MD status polling maps A to receipt and R to rejection, never payer adjudication, and atomically retains encrypted XML/matches/per-claim observations/event plus the Status cursor (`Sati.Api/Infrastructure/ClaimMdStatusProcessor.cs:11-13,19-136`). ERA polling uses an independent cursor; gathers all bounded listing pages, sorts ERA IDs, downloads 835 and commits evidence/payment effects/cursor together (`Sati.Api/Infrastructure/ClaimMdSandboxPoller.cs:54-115`; `ClaimResponseIngestion.cs:33-128`). These are implemented adapters; live account/feed behavior is unverified.

Corrections are explicit records, not silent changes to sent files: frequency 1 resubmission, 7 replacement and 8 void with payer claim number where required. The shared lifecycle rule decides allowed actions from latest response and standing adjudicated claim. Waiting/uncertain/review states do not permit ordinary corrections (`Sati.Contracts/V1/ClaimCorrectionRules.cs:7-17,83-144`). The API freezes correction facts in a period transaction, requires exact approved financial amendment identity, and preserves originals (`Sati.Api/Endpoints/BillingCorrectionEndpoints.cs:138-220`). Financial note amendments impose a review hold, reject stale original versions and refuse approval of changed financial facts while Sending/OutcomeUnknown is unresolved (`Sati.Persistence/Data/NoteAmendmentBilling.cs:12-48`). Local claimed-note correction remains unavailable.

## Part 4 — Idempotency and failure recovery

**Evidence classification: Implemented but incompletely tested internally; external duplicate-safe submission and production recovery are Not established.** This classification should remain bounded even after the inspected synthetic tests pass.

| Operation | Actual duplicate protection | Boundary/limitation |
|---|---|---|
| Note→claim line | Unique ClaimLine.NoteId, precheck, period transaction | Prevents two internal original claim lines for one note; does not prevent multiple external submissions of the retained line. |
| Period submit | State replay plus Status concurrency token and period lock | A repeated submit does not re-promote or externally transmit the period. |
| 837 generation | Normalized GUID key scoped to agency+actor, unique index, immutable exact bytes; conflicts on mismatched period/mode/profile; control-number unique index | Same key replay is protected. A fresh key is a fresh generation; another Billing user has another key scope. |
| Exact-file queue | Unique EdiGenerationId dispatch; repeat returns same dispatch; composite agency/account/generation FKs | One dispatch per generation, not one original claim submission for its entire lifetime. |
| Period uncertainty | Queue lock refuses another generation while any prior dispatch is Queued/Sending/OutcomeUnknown | Accepted terminal dispatch does not trigger this block. |
| Worker | Persist Sending before network; select Queued only; dispatch lease; zero-retry execution strategy across upload | At most one attempt per retained dispatch through this worker, at the cost of manual quarantine after crash/unknown. |
| Manual response intake | Raw/semantic/document/payment identities; unique indexes; receipt+matches+outcomes+deposit+audit transaction; replay existing receipt | Exact or re-enveloped duplicate posts nothing twice. Different payment identity for the same claim is preserved as a separate review event. |
| Connector feeds | Account/feed/artifact uniqueness, revision cursor, processing+cursor transaction, SQL poll/request leases | Incomplete/unmatched/duplicate pages pause feed; no implemented automatic skip or reconciliation of an unmatched feed item. |

Database proof locations: `Sati.Api/Data/ApiDbContext.cs:492-515` (period status, claim-note uniqueness, EDI key/control indexes); `Sati.Persistence/Data/ClearinghousePersistenceModel.cs:32-105` (dispatch, attempt, checkpoint, receipt indexes/FKs). EF write guards prohibit changing/deleting generation, attempts and receipt evidence (`ApiDbContext.cs:833-857`; `ClearinghousePersistenceModel.cs:155-194`). These are application and relational protections; privileged SQL bypass resistance requires separately verified database grants/denies.

### What happens when the external outcome is unknown

Before uploading, the worker checks key/encryption availability while still Queued. It then commits Sending before invoking the connector (`ClearinghouseDispatchWorker.cs:73-125`). Exceptions after this boundary are OutcomeUnknown; malformed/inconsistent connector output also yields unknown. It never equates a timeout with nonreceipt (`:127-145`). If a process dies after Sending but before recording a completed attempt, Sending remains stored without an attempt. Restart selects Queued only; neither Sending nor OutcomeUnknown is automatically retried (`:55-71,194-223`). If the vendor received the file but final database evidence commit fails, the durable Sending state remains quarantined and emits a safe error (`:155-190`).

Reconciliation is an agency Admin operation serialized with active upload and period writes. It checks exact current revision/account/generation/filename/hash/PCN/D9 evidence and dated attestation. ConfirmedReceived records retained manual receipt evidence; ConfirmedNotReceived requires support-case evidence, retains a distinct terminal state and does not resend. Audit explicitly states `byteIdentityUnverifiedByApi=true`: the API validates the Admin's assertion, it does not independently certify the vendor's file bytes (`Sati.Api/Endpoints/ClaimMdReconciliationEndpoints.cs:19-163`). Original attempt/receipt evidence remains unchanged. A later send requires a separately generated file. This is a sound conservative internal distinction between known no-send, recorded receipt and uncertainty; it is not an exactly-once external guarantee.

Claim.MD stable remote identity is `SATI1-{namespace}-{agencyId}-{periodId}-{noteId}`, sent in REF D9, while CLM01 includes the individual generation control number (`Sati.Contracts/V1/ClaimSubmissionIdentity.cs:16-34`; `Professional837Formatter.cs:91-99`). Onboarding records that an Admin confirmed the dedicated test account and remote_claimid-only duplicate field; it does not remotely validate the setting. External duplicate suppression, delayed-acceptance behavior, correction semantics and ability to prove nonreceipt require actual vendor/account acceptance evidence. `PAYER_BILLING_CERTIFICATION.md` and `CLAIMMD_SANDBOX_RUNBOOK.md` describe these gates; checked narrative claims from earlier work were not treated as new results.

### Significant code-inspected gaps, without a reproduced exploit

1. **A fresh original-file identity can bypass lifetime duplicate-submission protection.** Original EDI generation does not query successful prior generation/dispatch/claim-lifecycle history; with a new GUID it creates another full frequency-1 file (`ApiEndpoints.cs:7198-7260`; `ServerEdiGenerator.cs:39-40`). Queue blocks prior transmission for the same generation and period-level Queued/Sending/OutcomeUnknown, but not a prior AcceptedByClearinghouse for another generation (`ClearinghouseDispatchEndpoints.cs:104-129`). Worker/status/remittance processing leaves BillingPeriod.Status submitted, so the export Status==1 requirement still holds. WPF staging suppresses previously progressed/generated periods (`ViewModels/Billing/BillingSubmissionsViewModel.cs:816-823`), but this is not an API constraint. An authorized direct API caller can therefore take the source path to another original dispatch; whether Claim.MD rejects its stable D9 as duplicate is external and unverified. Existing same-file and unknown-outcome tests do not establish fresh-key-after-acceptance safety. Current actual transport is default-off/test-only, lowering immediate real-money impact, but this needs an explicit server lifecycle gate before live billing.

2. **Full compliance is checked at export, not again at queued external release.** Queue/worker check account/test/profile and note amendment version; the worker's guard only calls `NoteAmendmentBilling.ValidateLineVersionAsync` (`ClearinghouseDispatchWorker.cs:73-115`; `NoteAmendmentDispatchGuard.cs:9-20`). It does not invoke the full form/compliance export gate. An attestation can be revoked after financial records exist: revocation commits a new attestation and linked billing-review flags without changing the immutable claim (`ApiEndpoints.cs:8554-8615`; `ApiEndpoints.FormNoteAttestation.cs:403-443`). A form/compliance change between generation and eventual upload is therefore not visibly covered by the dispatch gate. This scenario was not executed. Before production activation, decide/enforce whether queued files must be cancelled/revalidated on such changes and test the intervening timing.

3. **Automated feed safety can become operational blockage.** Any unmatched account feed item, duplicate payment conflict, ambiguous source or bounded-page overflow leaves the cursor unchanged. The next poll meets the same item again. This avoids silent loss but no general account-feed quarantine/skip/reconciliation adapter was found; it needs an owned operator recovery process and alerts (`ClaimMdSandboxPoller.cs:34-47,85-115`; `ClaimResponseIngestion.cs:69-88`).

4. **The 835 worklist reduces explanation detail.** Parser accepts LQ but does not project RARC; only the first CAS group/reason is retained (`Sati.Contracts/V1/ClaimResponseReader.cs:302,361-402`). Financial totals include adjustments and encrypted original bytes preserve evidence, but actionable denial explanation can omit later reasons. `AGENDA.md:9023-9025` records the deferral.

## Founder explanation

Idempotency means repeating **the same identified operation** adds no extra effects. In Sati the GUID of file generation, identity of retained dispatch, and hashes/identities of response receipts do this at different boundaries. It does not mean any later command with a new GUID is harmless. A database transaction commits related database rows together; it cannot atomically include an external clearinghouse and local database. That is why the dispatch outbox saves intent before sending and stores uncertain outcomes rather than automatically retrying. A durable checkpoint commits only after a response and its effects are retained, allowing polling to resume safely after restart. These are strong internal design choices, but vendor duplicate detection and operational reconciliation remain separate evidence the owner must obtain.
