**Classification: Partially implemented.** Packaging, guarded installation, compatibility detection and manual release checks exist. Mandatory update enforcement, staged rollout and automatic rollback are not established.

* Per-user install roots and separate shortcuts/uninstall registry entries are documented in `installer/README.md:3-14` and implemented in `Install-SatiDemo.ps1`/`Install-SatiLocal.ps1`. The latest historical publication record is `AGENDA.md:52-63`: release 1.3.37 installer hashes and the two distribution folders, isolated acceptance on LONGCHENPA, and external-machine attestation **unverified**. The record is evidence of what the release process reported, not an independent installer test in this review.
* There is no observed in-app update feed, download/install scheduler or mandatory-update client. Settings/release notes report installed versions. Running an external installer is the update operation.
* Installation refuses running Sati processes (`Install-SatiDemo.ps1:98`; Local installer `:142`; `installer/Sati.LocalBootstrap/Program.cs:17-27`). The bootstrap independently extracts files and launches a hidden PowerShell installer without requiring the main desktop app to launch (`Program.cs:40-69`), so repair/reinstallation remains possible if the application cannot start.

There is no observed old-version snapshot, atomic directory switch, verified post-install launch gate or automatic restoration of earlier binaries. An interruption between copies can leave an incomplete installation; manually rerunning a reviewed package is the available recovery mechanism. This is a source-derived failure possibility, not a reproduced installation failure.
* The installer executable is not code-signed (`installer/README.md:86`; the builders do not invoke signing). The embedded LocalDB MSI is independently Microsoft-signed; that does not authenticate the Sati installer. SHA-256 checks detect differences against a trusted checksum but do not by themselves prove publisher identity.

## Part 7 — Backups and disaster recovery

**Classification: Not established for end-to-end recovery; the rehearsal adapter is partially implemented.** A restore helper exists, but tested service recovery, accepted RPO/RTO and preservation/reconciliation of later legitimate writes are not demonstrated by source.

* Historical deployment facts in `DATABASE_ENVIRONMENTS.md:142-167`: Azure SQL **Database**, logical server `sati-demo-satilogica-central`, `SatiDemo`, Central US, General Purpose serverless `GP_S_Gen5_2`, public endpoint with bounded outbound-IP rules, API Windows App Service Free F1. The document reports Entra-only SQL, API system-managed identity and SSN Key Vault. These are historical assertions tied to prior deployments. Current live SKU, backup redundancy/retention and identities require bounded metadata inspection; Azure offering a feature is not proof it was enabled.
* Source pins exactly this Demo database for `scripts/Invoke-DemoRestoreVerification.ps1:39-45`. The proposed rehearsal requires a new RunId, approved historical manifest and `-RunRehearsal`; WhatIf returns before Azure/SQL/file changes (`:49-92,109-119`). It issues Azure SQL point-in-time restore into a uniquely named `SatiRestoreCheck_<guid>`, checks resource ownership, compares historical database instance ID, complete migration ID inventory and selected table counts (`:247-319`), then deletes only confirmed owned scratch (`:337-355`). Local evidence captures state/cleanup/failed writes; uncertain creation is classified instead of blindly reusing a name.
* It is an **inspection rehearsal**, not a failover/cutover/recovery tool. It does not repoint API connections, bring up a recovered service, test blob/key access, test app workflows, replay post-restore valid writes or merge restored/original timelines. It probes aggregate inventory, not full record/content integrity. It does not fix authorization/network settings. `OPERATIONS.md:231-246,270-320` explicitly says it has not run against Azure and a real rehearsal requires separate approval. `DECISIONS.md:6420-6435` confirms the intended scope.
* `scripts/Test-DemoRestoreVerification.ps1` injects fake Azure/SQL operations and tests safety/error paths. That verifies orchestration behavior, not a restorable cloud backup. No dotnet-test/CI reference to this script was found in the inspected test projects/workflow. The parent can report it separately if executed safely.
* No numeric accepted RPO/RTO appears in inspected repository guidance. RPO means acceptable data loss measured in elapsed writes/time; RTO means acceptable time to restore usable service. A script timer or cloud retention setting is not an approved objective or proof the objective is achievable.
* Existing append-only events/versions/financial IDs can help a human compare histories but are not a complete event-sourced replay model. Restoring a database removes all writes after the restore point from that recovered timeline, including valid notes, approvals, audits and dispatch receipts. Merging later state safely must preserve identities, tenant ownership, immutable records, dependencies, external submission outcomes and duplicate constraints. No implementation/test proves that reconciliation. An external claim can survive a database restore, so blindly regenerating/retrying after restoration risks duplicate external financial effects despite restored local keys.
* Signature data spans database rows, immutable blob originals/evidence and versioned wrapping keys. `OPERATIONS.md:561-567` explicitly requires recovering them together; neither the SQL rehearsal nor an inventory count demonstrates recovery of those dependencies. Local SSN protection also depends on the Windows-account key, so merely copying/restoring SQL bytes is not proof of decryptability on another workstation.
* Local pre-migration backups live on the same workstation and protect the migration boundary only; no inspected periodic independent backup, off-device encrypted recovery, automated validation, prune policy or drill is implemented (`SqlLocalDatabaseMaintenance.cs`; `BACKGROUND_WORKERS_HANDOFF.md:297-303`). This should be assessed as protection of a personal PHI store, not as an existing cloud Production service.
* Microsoft's managed database infrastructure can supply backups/storage durability according to the selected service and configuration. Sati remains responsible for discovering what is configured, objectives, authorized restore/cutover, identity/key/blob recovery, application correctness, financial reconciliation, audit preservation, operators and rehearsals. The report should describe live metadata from the parent, not assume a default redundancy/retention from documentation.

## Prioritized operational risks and useful external-architect answers

1. **Critical gate before PHI service/pilot: recoverability is not demonstrated.** Live settings establish a seven-day local-redundant backup window without long-term retention, not recovery success. Establish accepted RPO/RTO, authorized restore/cutover, database/blob/key consistency, later-write recovery and external-billing reconciliation. Rehearse and retain evidence. No exploit or data loss was demonstrated here.
2. **Critical gate before PHI service/pilot: alert routing and response evidence.** Exact planned alert resources are currently absent. Source watchdog and health UI cannot substitute for live external alert receipt, owner/escalation/after-hours procedure and detection when the watchdog itself stops.
3. **High: audit completeness/integrity and security-failure coverage.** Ordinary API note creation/edit/Pending-to-Logged submission/deletion lack general action events; local creation/edit coverage does not carry through to Demo API. Add explicit atomic PHI-free clinical action events and meaningful rollback/completeness tests. Verify deployed deny/grant/identity separation, protect retained operational evidence and design appropriate denied-action/security alerts. Broad DB write roles undermine claims of database-enforced audit immutability.
4. **High: deployment/schema rollback compatibility.** Prove supported old/new client/server/schema combinations, expand/contract sequencing and explicit rollback state. Banner-only fingerprint mismatches permit incompatible operations; local installer byte replacement plus application-owned migrations lacks independent schema recovery.
5. **High before PHI hosting: verify provider/global log redaction and access/retention.** Full exception logging remains outside the sanitized incident envelope. This is an investigation requirement, not a confirmed PHI leak.
6. **Medium: billing observability.** Add a controlled read-only reconciliation view listing approved note IDs and current exclusion facts, plus deliberate event/metric coverage where historical reasoning is necessary. Candidate absence should be distinguished from failed delivery because the queue is a query.
7. **Medium: automated tests must exercise the real provider/deployment boundary.** CI SQLite/source checks are not lock/migration/deployed-permission/restore tests. Add separately approved private SQL rehearsals and protected infrastructure acceptance; retain exact source/bundle/fixture/result evidence.
8. **Ordinary release improvement: installer signing and crash-safe replacement.** Authenticate installers, stage/validate a complete new directory and document a tested manual rollback/repair flow without exposing/copying PHI.
