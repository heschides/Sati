## Part 2 — Authentication, authorization, and tenant isolation

Suggested area classification: **Implemented but incompletely tested**. The code contains substantial request authorization and executable denial tests. This is not an external penetration test or verification of the deployed Azure identity/security configuration.

### Authentication mechanics

* `Sati.Api/Security/PasswordVerifier.cs:8-28` derives a 32-byte password verifier with PBKDF2-HMAC-SHA256, 100,000 iterations and a fresh cryptographically random 16-byte salt. Hash and salt are stored as Base64. Verification uses `CryptographicOperations.FixedTimeEquals` (`:31-54`). Unknown usernames run a decoy derivation (`:57-68`) and the API returns the same unauthorized response as a wrong password (`Sati.Api/Endpoints/ApiEndpoints.cs:1320-1343`). This establishes the format in source, not independently reviewed strength against current attacker hardware. There is no self-describing hash version/iteration format or automatic upgrade-on-login in these methods.
* Ordinary API account passwords are length-checked at 8–128 characters (`Sati.Api/Endpoints/ApiEndpoints.cs:11009`); initial administrator workstation bootstrap separately requires 16–128 (`Services/AdministratorBootstrap.cs:44-46`). This reviewer found no implementation of MFA, external identity federation/OpenID Connect, compromised-password checks, or persistent account lockout in this authentication surface. Those capabilities must not be represented as present.
* API login limits inputs before database/password work (`ApiEndpoints.cs:1304-1306`). A singleton in-memory per-username limiter allows twelve attempts per minute and resets on successful login (`Sati.Api/Security/LoginAttemptGuard.cs:5-42`). The host-wide fixed-window login limiter allows 120 attempts/minute, zero queued requests (`Sati.Api/Program.cs:200-205`). These stateful limits live within one process; they are not a distributed or restart-persistent lockout mechanism. The global bucket also means sign-in availability can be exhausted for all callers to that instance. This is a design limitation, not a demonstrated exploit.
* The API reads the user by username, verifies the password, then rechecks enabled state, security version, credential snapshot, agency, legacy role and permissions before issuing a token (`ApiEndpoints.cs:1320-1340`). Successful login writes `authentication.succeeded` before issuing the bearer (`:1346-1357`). Failed login writes only an operational warning with the remote IP (`:1342`), not a durable `AuditEvent`.
* `Sati.Api/Security/TokenIssuer.cs:25-52` issues an HS256 signed JWT. Claims include user ID, agency ID, role/name, random `jti`, initial authentication time, database instance ID, and account `SecurityVersion`. Permission flags are deliberately absent from the token. The signing material comes from bound server authentication options; its value was not inspected. The startup guard requires at least 32 characters, token lifetime 5–60 minutes and session-renewal cap no greater than 1,440 minutes (`Sati.Api/Program.cs:34-41`). The **source defaults** are 30-minute access tokens and 720-minute renewal cap (`Sati.Api/Infrastructure/ApiOptions.cs:5-12`). Actual live values, secret custody, rotation procedures, and key access controls are unverified.
* ASP.NET JWT middleware validates issuer, audience, signing key and lifetime with 30 seconds clock tolerance (`Sati.Api/Program.cs:160-176`). After cryptographic validation, `ValidatedActorFilter` reloads enabled/version/agency/role from the database and fails closed on unsupported permissions or invalid database-instance identity (`Sati.Api/Security/TenantAccess.cs:107-131`). Thus possession of an otherwise valid JWT is not sufficient after account disablement or version revocation.
* Session renewal is an authenticated `/api/v1/auth/renew` call using an existing bearer, not a separate long-lived refresh token (`ApiEndpoints.cs:1365-1399`). It retains the original authentication time and refuses renewal after the configured cap. An already expired bearer cannot authenticate renewal. **The 12-hour default is a renewal limit, not an exact hard cutoff for every HTTP request:** a bearer renewed just before the cap may remain valid until its own expiration; the ordinary filter does not test `sati_auth_time`. Chat separately uses the earliest of token expiry and original session cap (`Sati.Api/Endpoints/ChatStreamEndpoints.cs:92-105`).
* Password reset/change and administrator disable/re-enable/session revocation increment the retained `SecurityVersion`. Lifecycle writes are serializable, revalidate the administrator inside the transaction, preserve the user and caseload, refuse self-disablement, and exclude platform identities (`Sati.Api/Endpoints/AccountLifecycleEndpoints.cs:15-60`; password routes `ApiEndpoints.cs:1492-1547`; shared policy `Sati.Contracts/V1/AccountSessionRules.cs:14-37`). Both EF models mark version as a concurrency token (`Sati.Api/Data/ApiDbContext.cs:126`; `Sati.Persistence/Data/SatiContext.cs:381-384`). Revocation is account-wide; no per-device session registry or individual `jti` denylist was found. It prevents subsequent protected calls, not recovery of data already delivered or retroactive cancellation of every operation already authorized in flight.
* The cloud desktop uses login response identity, stores the bearer in `CloudApiClient` instance fields, attaches it to Authorization headers, and replaces it under a lock (`Data/Cloud/CloudAuthService.cs:16-21`; `Data/Cloud/CloudApiClient.cs:21-31,93-113,526`). Renewal happens within a five-minute margin (`CloudApiClient.cs:44,401-445`) and generation guards prevent an older sign-in/renewal response replacing newer credentials (`:434-438`). No on-disk bearer persistence was found in this path. Passwords necessarily become a managed string for JSON login; assigning `string.Empty` in `CloudAuthService.cs:66-69` does not securely erase the preceding immutable string.
* The workstation local path is separate: `Data/AuthService.cs:16-57` authenticates against its EF database, copies persisted permissions/enabled/version into a session with empty hash/salt, and records successful authentication. It does not implement the API's decoy username handling or login throttling. `Data/LocalTenantAccess.cs:23-108` checks current stored account and casework scope per operation. This local direct-database environment is the owner's working system, not evidence of a distributed enterprise security boundary.

### Permissions and agency boundaries

`Sati.Contracts/V1/UserPermissions.cs:8-34` defines independent CaseManagement, Supervision, Administration, Billing, AgencyWideSupervision and RepresentativePayee flags. `UserPermissionRules` interprets these (`:50-77`). Legacy job labels are compatibility/display data; `PlatformOperator` is an orthogonal identity restricted by the API filter. Supervisory access requires the Supervision capability plus same agency and assigned supervisee, unless agency-wide reach is granted (`Sati.Contracts/V1/CaseloadTransferRules.cs:80-101`). Administration contributes agency-wide reach only when the operation also requires supervisory capability. It does not inherently grant Billing or CaseManagement.

* Every mapped normal `/api/v1` route inherits `RequireAuthorization` and `ValidatedActorFilter` through one root group (`Sati.Api/Endpoints/ApiEndpoints.cs:42-94`). Login is explicitly mapped outside the group. The filter strips any incoming server-permissions claim before adding the database-derived flags (`TenantAccess.cs:133-143`). Client-supplied `userId`, `agencyId`, and person identifiers are selectors, not an identity proof.
* `TenantAccess.CanAccessUserAsync` first checks current actor facts, then permits own casework only with CaseManagement or scoped supervision via shared rules (`TenantAccess.cs:10-38`). `CanAccessPersonAsync` additionally checks the person's agency (`:63-66`); `OwnedPeople` joins the persisted owner and checks both owner/person agency plus enabled/version/role/permissions (`:80-90`). Examples: selected caseload `/caseload` (`ApiEndpoints.cs:1987-1994`), journal reads/writes (`:2114,2132`), person save (`:2303`), consumer contacts (`:3122,3145,3169,3203`), and note joins (`:4951,5100`). Billing uses its separate narrow permission and tenant scope; a billing-only account does not gain clinical narrative access (`Sati.Api.Tests/BillingPrivacyTests.cs:14-27`).
* User creation derives `AgencyId` from the validated actor (`ApiEndpoints.cs:1431-1452`). User management uses `UserManagementRules` to prevent supervisors assigning privileged capability or taking over an assigned privileged account (`Sati.Contracts/V1/UserManagementRules.cs:37-100`; `ApiEndpoints.cs:1466-1488,1500-1517`). Account management rejects other-agency targets by scoped lookup (`AccountLifecycleEndpoints.cs:30-38`).
* Cross-tenant operational support is restricted to `/platform`, incident submission and narrow own-profile/password operations (`TenantAccess.cs:146-155`). Support does not thereby gain casework/billing routes. One concrete scope detail: `/auth/renew` is not in this platform identity allowlist, so a PlatformOperator cannot use the ordinary renewal endpoint. This is a minor behavior limitation, not a tenant break.
* **Database enforcement is incomplete for general tenancy.** The current Sati contexts/migration chain contain no blanket EF `HasQueryFilter` or SQL `SECURITY POLICY`/`SESSION_CONTEXT` implementation. The core Person→User and Person→Agency relationships are independent single-column foreign keys (`Sati.Persistence/Data/SatiContext.cs:453-464`); SQL can represent an inconsistent owner/agency combination. Newer models add selected composite tenant foreign keys, but do not retrofit the whole data model. Current access safety therefore rests primarily on disciplined explicit query predicates, scoped workflow services and tests. Future row-level security described in the platform design is intention. This does not demonstrate an exploitable cross-tenant route; it raises the consequence of a future omitted predicate or unrestricted database access.
* Historical documentation must not be accepted as the current implementation: `API_SECURITY_AUDIT.md:441-460,549-552` still calls four owner-only routes and permission-claim shadowing open. Current sources above resolve those cases. `ConsumerPermissionRevocationTests.cs:186-277` explicitly tests mismatched person/note tenant markers. Conversely `ARCHITECTURE.md:784-790` contains a historical unapplied-migration warning; this assessment did not query real deployment state, so it cannot reconcile that claim against later release history.

## Security-relevant logging qualification

`AuditTrail` adds an actor/agency/resource/action/correlation/metadata event to the operation's current EF context (`Sati.Api/Security/AuditTrail.cs:5-23`). It does not intercept every HTTP read, denial, or exception. Authentication denials and generic `Unauthorized`/`Forbid` returns therefore do not automatically become durable audit events. `ValidatedActorFilter` contains returns but no denial-audit writer (`TenantAccess.cs:108-155`). `TenantAuthorizationTests.cs:1550-1563` establishes that a denied cross-agency write does **not** create a success audit; that is not proof of an attempted-access audit. Application append-only checks prevent tracked changes/deletes (`Sati.Api/Data/ApiDbContext.cs:821-891`); they are not independently protected storage against a privileged SQL administrator or raw bulk commands.

The API has two exception channels. Its curated incident recorder fingerprints type/HResult/method instead of storing unrestricted exception text (`Sati.Api/Infrastructure/ApiIncidentRecorder.cs:20-36,44-63`) and ignores unauthenticated exceptions (`:14-16`); incident persistence failure is swallowed (`:38-40`). Separately `Sati.Api/Program.cs:218-232` passes the full exception to `ILogger.LogError`, while JSON console output is configured at `:25-28`. This is a concrete unsanitized logging path; it can disclose sensitive exception messages/inner exceptions if any upstream exception carries them. No real sensitive disclosure was observed or demonstrated. The existing SSN-path log-capture test (`Sati.Api.Tests/SsnAndFormApiTests.cs:225-241`) checks successful/validation/form paths, not arbitrary unhandled exception payloads. A synthetic sentinel injected through the actual unhandled exception pipeline and captured at every sink would address this missing assurance.

The desktop's error log is more selective: `Services/AppErrorLog.cs:175-191` stores exception type/HResult/target/stack but omits Message and inner Message. It rotates at 5 MiB/file, 50 MiB/directory and 30 days (`:15-17,134-155`). This source policy is separate from API/App Service telemetry retention and access, which were not inspected live.

### Guarantees not established by this inspection

* Complete negative JWT matrix at the actual API boundary (wrong signature/issuer/audience/algorithm, expired bearer, duplicate identity claims); source config and selected malformed security-version tests are stronger than nothing but not that entire matrix.
* Restart/multi-instance login limiting, enterprise authentication/MFA, signing-key custody/rotation compromise handling, or independently measured password-hash security.
* Exhaustive tenant-route coverage as the surface grows; whole-schema tenant ownership enforcement; direct SQL identity least privilege; atomic revocation of every in-flight request.
* Live encryption/TLS/Key Vault/managed identity/firewall configuration or externally audited security posture.
* Broad synthetic secret/narrative redaction failure injection at all operational log sinks and retention/access controls for hosted logs.
* Independent penetration testing, legal/regulatory approval, HIPAA compliance, or enterprise readiness. `REGULATORY_CONCERNS.md:26-54` correctly separates these obligations from Azure infrastructure capabilities.

## Prioritized security implications for the main report

1. Before real multi-agency PHI use, independently review tenant and authorization boundaries, deployed identities/keys/network controls, all PHI release surfaces, and logging. Passing developer tests alone is not external assurance. This is a launch prerequisite; no current exploitable cross-tenant path was established here.
2. Review the full-exception API logging channel and add synthetic negative-path sink tests. The unsanitized implementation is present; actual data exposure remains unverified.
3. Consolidate and enforce tenant ownership in the database where needed, or explicitly document the application-predicate guarantee and monitor integrity anomalies. Selected composite foreign keys are useful, but blanket RLS/query filters are absent.
4. Define real agency identity requirements (MFA, provisioning/offboarding, recovery, privileged account controls, distributed throttling, secret rotation). Current custom password/JWT system implements account-wide revocation but does not establish these operational controls.
5. Bring review documentation in line with code and distinguish source defaults, historical execution claims, current executed tests and actual deployment evidence. Stale open findings should not be used to imply present vulnerabilities, and historical release claims should not be upgraded to observed configuration.
