## 2026-09-29 — Demo reset diagnostics must survive an interrupted worker

The 1.3.32 verification requests entered the reset queue but produced no outcome audit.
Host logs showed an early shutdown during the replacement invocation; they did not
identify which reset operation was active. The subscription remained enabled, managed
identity authentication and SQL access succeeded, and the reset's existing EXECUTE and
audit INSERT permissions were confirmed. No payment or permission change was indicated.

The shared reset runner now logs a request id and fixed stage name before blocking work.
Token acquisition is bounded to 30 seconds and baseline restoration to 240 seconds,
below the Function's 600-second lifetime. Cleanup and outcome writes have short bounds;
cleanup errors cannot replace the original failed stage. These bounds improve diagnosis
and failure handling but do not guarantee an audit after platform termination.
Executable PowerShell tests inject identity, SQL, seed, cleanup, and audit failures and
verify the actual control flow and redaction. Text-only script checks did not cover this.

An existing Function can be updated with a retained, hash-verified code package using
`Publish-DemoRefresh.ps1 -ExistingAppOnly`. That path validates the exact Demo target and
runtime without creating resources, assigning identities, or changing settings. A
package-only pass permits review before deployment. The queue still permits one delivery;
an interrupted reset is reviewed before a deliberate new verification request.

Rejected: increasing retry counts on a destructive reset, extending the Function timeout
without locating the stalled stage, or changing SQL permissions/firewall rules when the
existing identity already has the required access.
