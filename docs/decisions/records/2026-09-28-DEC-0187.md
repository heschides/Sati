## 2026-09-28 — Karuna prerequisite refinements after the second review

Codex reviewed the corrected Karuna documents and proposed concrete P0 and P1 plans. Claude checked
every finding against the code, confirmed all six, and added four. Josh approved four refinements.
None changes D-1 to D-13; each corrects how one of them is implemented.

### Correction to D-11: `AuditCsv` stays in Sati

D-11 listed `AuditCsv` among the product-neutral types to introduce, because its header names no
agency. The type is not neutral:

- `AuditCsvRow` has an `int ActorUserId` (`Sati.Contracts/V1/AuditCsv.cs:10`, written at `:67`);
- its comments describe Sati's export workflow (`:17-30`).

It stays in `Sati.Contracts` with its row, header and export method. Only the spreadsheet-safe field
encoding — RFC 4180 quoting plus formula neutralization — is extracted into `SatiLogica.Contracts`.
`AuditCsv` then calls it, and a golden-output test proves Sati's export is byte-identical. That
encoding is the security-relevant part and the only part another product should share. Karuna's audit
export defines its own row with its own id types.

**Rejected:** moving `AuditCsv` as-is, which would put an `int` actor id into the platform; and a
neutral row type with an adapter, which adds a translation layer to protect a format no second
product uses.

### Platform identifiers are opaque

D-11's tenant actor, the audit envelope, and D-2's actor-store seam all carry principal and tenant
identifiers. Sati's are integers (`User.Id`, `AgencyId`); Karuna's are UUIDv7 `Guid`s. The platform
therefore identifies principals and tenants by product plus an opaque string. Each product converts its
typed keys at the boundary, and platform code only compares and serializes them. Tokens already carry
the user id as a string (`TokenIssuer.cs:34`). Inside each product, keys stay typed.

**Rejected:** a platform integer id, which Karuna cannot use; and generic `TenantActor<TUser, TTenant>`
types, which spread type parameters through every seam for no benefit.

### The Local migration runner lands before the chain moves

Nothing sets `MigrationsAssembly` (`App.xaml.cs:580`, `SatiContextFactory.cs:30`), so EF finds migrations
in `SatiContext`'s own assembly. The desktop migrates through that path: fresh-database provisioning
(`LocalDatabaseProvisioner.cs:34`) and the updater. Moving the chain first (handoff P5) would leave the
desktop with nothing to apply. Fresh Local databases would stay empty, and later migrations would never
reach Local Production.

So handoff P6 comes first:

1. `SatiLogica.Migrator` is built against today's chain in `Sati.Persistence`, and ships as a Local
   release.
2. P5 then moves the chain and repoints the runner in the same commit.

The runner grows from `tools/SatiUpdateReport`, which already mirrors the startup gate, backs up,
fingerprints and applies with `--apply`.

P5 must also repoint everything else that finds migrations through `SatiContext`'s assembly:

- `MigrationEffectAnalyzer` and `PersistenceAssemblyBoundaryTests`;
- the migration-assembly tests in `StabilizationTests.cs:1630-1756`;
- `tools/SatiComplianceSeed/Seeder.cs:175-176`;
- `scripts/Test-SchemaDrift.ps1:11`.

`scripts/Apply-Release1311Migrations.ps1` is marked historical. The per-migration Demo runners apply
SQL keyed by migration id and are unaffected.

**Rejected:** shipping P5 alone, which strands Local Production; and letting the desktop reference
`SatiLogica.Schema` temporarily, which D-12 rejects. Combining P5 and P6 into one release was possible
but gives a larger change a single chance to go wrong.

### Only the migrator and tests may reference `SatiLogica.Schema`

"Referenced by no runtime project" was too broad, since `SatiLogica.Migrator` is an executable that
must load the chain. The rule is:

- no product library, host or client references `SatiLogica.Schema`;
- `SatiLogica.Migrator` and test projects may.

The P1 guardrail enforces it.

### The project guardrail separates product from kind

The P1 manifest records `product` (platform, sati, karuna) and `kind` (library, host, client, test,
tool) as separate fields. A single "role" could not say both that `Karuna.Tests` is a test and that it
belongs to Karuna.

The rules are these:

- product-boundary rules read `product`;
- a test may reference only its own product and the platform;
- only tools may reference tools;
- a conditional `ProjectReference` is rejected until the reader supports it.
