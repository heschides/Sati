## Decision and reason

Use the [canonical coordination rules](../../../AGENTS.md#concurrent-thread-coordination): begin
with one main integration thread and one bounded independent investigation/review thread. Assign
each task explicitly, isolate additional writing in a dedicated worktree, record source inputs
and ownership, preserve dependencies and integrate one reviewed chunk at a time. Two threads is
a starting planning convention, not a product limit or a configuration change.

[The agenda](../../../AGENDA.md#parallel-work-assignments) owns task numbers, status, dependencies,
assignment and safe parallel eligibility. Keep its single main next-item pointer. The first
available parallel task is 1.4.1 resource-limit inventory, alongside 1.3.1 fairness design; source
inventory does not adopt a resource policy or implement runtime changes. Main verification of
1.2 retains its existing evidence owner and is not declared finished here.

Dedicated worktrees prevent overlapping file edits but do not resolve competing design choices
or isolate databases and machine capacity. Explicit scope, shared-owner review, actual evidence
and source-drift checks address those risks. Each secondary thread submits awaiting review; the
main thread reconciles current findings and documentation before marking integrated completion.

## Alternatives and limits

- A single thread avoids coordination but serializes independent review work; retain that option
  when tasks depend tightly on each other or machine/test resources are constrained.
- Multiple writers in one checkout risk mixed diffs and interference with active builds; use
  dedicated worktrees for additional writing threads.
- Several threads independently taking the main next task duplicate work and can adopt divergent
  policies; use one main pointer and explicit bounded secondary assignments.
- Starting many implementation threads immediately increases overlap and integration work; begin
  with one implementation/integration thread plus one investigation thread and reconsider later.

No subagent delegation, automation, task execution, runtime change, Git publication, migration,
cloud/security setting, real-data access or release is authorized by documenting this workflow.
Subsequent explicit task prompts govern their own bounded authority. D1–D4, existing release
rules, schema review and runtime-policy adoption requirements remain unchanged.
