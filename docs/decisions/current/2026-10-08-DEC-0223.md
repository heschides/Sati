# DEC-0223 — One Claim.MD HTTP exchange deadline

**Date:** 2026-10-08. **Status:** accepted for the second bounded local SATI-WRK-001 slice.
**Authority:** Josh directly requested the next task; the active agenda selected the existing
Claim.MD HTTP budget's response-body gap. This authorizes local source and synthetic verification.

## Context and choice

`ResponseHeadersRead` completes `HttpClient.SendAsync` at response headers. The former
45-second client timeout did not cover the connector's subsequent stream acquisition or reads.
A stalled body could therefore retain the coordinated request callback indefinitely.

`ClaimMdSandboxConnector` now owns one named 45-second HTTP exchange budget. Inside the
existing coordinated callback, after SQL admission and pacing, it creates a deadline with
`CancellationTokenSource(TimeSpan, TimeProvider)` and links it to coordinated caller cancellation.
The linked token covers sending/headers, stream acquisition and every body read; cancellation
is checked before sending and again before returning decoded content. `ConfigureHttpClient`,
used by production registration and test clients, sets the client timeout to infinite so the
connector deadline is the single timer owner. The API's existing injected `TimeProvider` supplies
the production clock and deterministic test clock.

Keep request/response/stream disposal and coordination cleanup on normal exception unwinding.
Keep the fixed host, disabled redirects/cookies, key validation, 16 MiB cap, default-off Demo
gate, SQL admission/command budgets, pacing, provider-wide quota, poller/reset and dispatch
locks unchanged. Add no retries. An upload deadline after committed `Sending` remains uncertain;
the existing worker records `OutcomeUnknown`, and neither state is automatically replayed.

## Alternatives and consequences

Keeping only `HttpClient.Timeout` leaves the body gap. Starting a fresh 45-second timer after
headers would extend the exchange budget. Retaining both a system-clock client timeout and the
provider-backed deadline introduces competing timers and undermines deterministic ownership.
Retrying a timed-out upload would confuse local cancellation with remote nonreceipt.

This is a cooperative HTTP I/O deadline, conditional on the handler/content honoring cancellation.
It is not a hard wall-clock bound for SQL admission or pacing, synchronous decoding/XML parsing,
disposal/SQL lock cleanup, an account turn or a whole worker pass. Final cancellation prevents
returning content after an observed expiry; it cannot interrupt synchronous CPU work or prove
remote nonreceipt. Total budgets, account fairness and aggregate capacity remain W8 work.

Microsoft's [HttpCompletionOption documentation](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption?view=net-10.0)
explains the headers-only client timeout boundary. Its
[CancellationTokenSource constructors](https://learn.microsoft.com/en-us/dotnet/api/system.threading.cancellationtokensource.-ctor?view=net-10.0)
document the provider-backed timer used here. These sources were checked October 8, 2026.
