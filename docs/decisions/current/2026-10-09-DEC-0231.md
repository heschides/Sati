# DEC-0231 — Retained EDI replay includes request kind

**Date:** 2026-10-09. **Status:** accepted; source implementation verified.
**Authority:** Josh requested duplicate-claim safeguards and compliance checks after adopting
the original-release policy in [DEC-0230](2026-10-09-DEC-0230.md).

## Choice and reason

`Sati.Contracts.V1.EdiReplayRules` owns equality of retained/requested billing period, test mode
and Original/Correction request kind. API original initial/recovery, API correction replay and
both transitional local original replay paths use it. Actor/agency/key lookup, API routing-profile
matching and current original export compliance remain authoritative adapter checks.

An original request cannot replay a correction's key. Frequency 1 is insufficient: a legitimate
linked Resubmit correction and an original both carry frequency 1. Wire-byte comparisons and
generation keys alone therefore cannot establish request kind. Correction replay uses the same
owner with explicit Correction identity, preserving its separate release purpose.

No new original-send permission, historical account fingerprint, schema, route or correction
action is introduced. Valid exact original/correction replay returns retained bytes without new
generation, correction-link, submission-event or audit effects.
