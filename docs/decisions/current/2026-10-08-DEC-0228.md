## Context and choice

Program configures SQL retries. Direct incident aggregation began an explicit transaction without
an owning execution scope, so EF could reject persistence after a request's single-attempt write
filter had unwound. A separate baseline also showed a retrying outer scope was not refused.

`IncidentAggregator.UpsertAsync` checks cancellation, then refuses an active retrying execution
strategy before acquiring the gate or creating a context. Its named `IncidentSingleAttempt`
zero-retry strategy contains the entire existing transaction, query, save and both commit paths.
Preserve short-lived contexts, gate release, current SQL query/transaction behavior and valid
single-attempt callers. The matching
[EF Core 10.0.10 source](https://raw.githubusercontent.com/dotnet/efcore/v10.0.10/src/EFCore/Storage/ExecutionStrategy.cs)
shows that nested execution follows the active outermost strategy; a nested zero-retry strategy
cannot replace a retrying caller.

## Alternatives and consequences

Wrapping only SaveChanges leaves transaction ownership and the immediate-replay commit branch
outside the boundary. Using the configured retrying strategy risks repeating an ambiguous write.
Relying on the endpoint filter misses direct error-handler recording after it unwinds. Refusing
all active scopes would reject valid single-attempt callers. These alternatives are rejected.

The stored last reference supports immediate replay/enrichment without another occurrence.
It is not a historical deduplication ledger; A/B/A can count A again. No new schema or locking
policy is added. Save/cancellation faults roll back when uncommitted; an acknowledgement fault
after commit can leave durable state while the caller receives failure. No automatic replay or
success inference follows. Microsoft's
[commit-ambiguity guidance](https://learn.microsoft.com/en-us/ef/core/miscellaneous/connection-resiliency#transaction-commit-failure-and-the-idempotency-issue)
explains why that outcome needs reconciliation.
