# DEC-0222 — Recoverable agency faults in the note-abandonment worker

**Date:** 2026-10-08. **Status:** accepted for the bounded local SATI-WRK-001 slice.
**Authority:** Josh requested review of the consolidated Sati summary and completion of the
next task; the active agenda selected per-agency note-worker failure isolation.

## Context and choice

The worker visits agencies serially. An exception in one agency's transactional sweep previously
ended the pass before later healthy agencies. Keep the existing global SQL sweep lock and Demo
reset lease; catch only explicitly recoverable faults from the individual sweep call.

The API worker owns this operational classification. Admit EF `DbUpdateConcurrencyException`
and SQL deadlock-victim errors only when every entry in the nonempty `SqlException.Errors`
collection is number 1205 with severity below 20. Recognize only the deliberate EF
`DbUpdateException` and `RetryLimitExceededException` wrappers; do not traverse arbitrary
exception chains or classify by message text. Cancellation overrides continuation. Shared agency
discovery, connection and coordination failures remain outside the catch; timeouts, fatal,
mixed SQL and unknown failures propagate.

On a recoverable fault, leave that agency due and global completion false, log agency ID and
exception type without the exception object/message, and continue to the next agency. Count only
the sweep result returned after commit and cleanup. A failed agency is invoked once per worker
pass and can run again on the existing hourly cadence; a successfully completed agency remains
skipped that day. An at-limit batch remains due. This adds no worker-level immediate retry and
does not change the sweep's execution strategy, 100-note bound, revision predicates, atomic
note/audit transaction, shared business rules or default-off setting.

## Alternatives and consequences

A blanket database catch would conceal connection outages, uncertain commits or broken shared
coordination. Treating every transient provider error as agency-local has the same problem.
Checking only `SqlException.Number` overlooks additional errors in its collection. Generic inner
exception traversal can convert an unknown outer failure into an apparently recoverable one.

An immediate worker retry would delay healthy agencies and multiply the existing EF retry owner.
Changing lock scope or adding parallel sweeps would require separate quota, reset and multi-host
proof. Those choices are deferred. This continuation policy closes a failure gap; it supplies no
maximum healthy-agency wait, total-pass budget, structural tenancy or runtime activation evidence.

SQL 1205 is deliberately narrow because SQL Server rolls back a deadlock victim's transaction;
see Microsoft's [deadlock guidance](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide).
The existing EF retry owner and ambiguous-commit limits remain as described in Microsoft's
[connection resiliency guidance](https://learn.microsoft.com/en-us/ef/core/miscellaneous/connection-resiliency).
Injected provider exceptions test classification, not a real SQL deadlock or retry-exhaustion event.
